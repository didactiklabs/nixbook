# AI Agents Guide

## Project Overview

**Nixbook** is a reproducible NixOS configuration repository providing declarative system management for multiple machines using the Nix programming language.

**Repository:** `git@github.com:didactiklabs/nixbook.git`
**Primary Goal:** Create a robust, reproducible NixOS environment with modern Wayland display servers and UEFI boot support.

## Key Statistics

- **Nix Files:** 178 files (~16,000 lines of code)
- **Active Machines:** 5 (totoro, anya, nishinoya, tanjiro, hanamichi)
- **Home Manager Modules:** 34 (29 standalone files + 5 subdirectories)
- **NixOS Modules:** 19 files
- **Custom Packages:** 20
- **CI/CD Workflows:** 2
- **NixVim Plugins:** 25
- **VSCode Extensions:** 32
- **Pinned Dependencies:** 41
- **Assets:** 46 files

## Core Tools

- `NixOS` - Linux distribution with declarative configuration
- `Colmena` - Declarative machine deployment tool
- `npins` - Nix dependency pinning and source management
- `Home Manager` - User-level configuration management
- `agenix` - Age-based secrets management
- `Disko` - Declarative disk partitioning
- `Lanzaboote` - UEFI Secure Boot support

## Directory Structure

### Configuration Layers

```
profiles/{hostname}/              Machine-specific configurations
  ├── configuration.nix
  ├── default.nix
  └── {username}/                 User-specific overrides
```

- `devenvModules/` - Shared devenv config module imported by nixbook, hephaestus, and aletheia via npins

A copy refreshes independently, and rotating refresh tokens can then log the host or the workspace out. To resync with upstream: diff `customPkgs/nixbook-shell/src/` against a fresh checkout and merge by hand. Installed read-only at `~/.config/quickshell/nixbook-shell`, run by the `nixbook-shell` user service. Everything is driven through the `nixbook-shell` wrapper (`nixbook-shell` starts it, `nixbook-shell ipc call <target> <fn>` drives panels), which injects the ~40 runtime tools upstream shells out to into `PATH`. **Settings: every key set in Nix is locked, every other key is editable.** The shell owns `~/.config/nixbook-shell/config.json` — it writes the full default tree on first run and rewrites it live from the in-shell Settings panel (`Mod+Escape`), so it is a real mutable file, never an `xdg.configFile` symlink (a store path would make the panel fail). The module has only two options, like the other modules: `enable` and `settings`. `settings` is a submodule of **typed options generated from the shell's built-in defaults** (`customPkgs/nixbook-shell/builtin-defaults.json`, upstream's `Config.qml` default tree minus runtime keys; regenerate with `nixbook-shell config builtin > customPkgs/nixbook-shell/builtin-defaults.json`, which runs only the `Config` singleton against an empty `XDG_CONFIG_HOME` inside the graphical session and opens no window). Each leaf is `nullOr <type inferred from the default>` with default `null` (= not set in Nix), so a misspelt key fails evaluation ("The option `…settings.bar.bottomm' does not exist"); `visible = "shallow"`keeps the ~450 leaves out of docs/MODULES.md. The shared values in`homeManagerModules/nixbookShellConfig/settings.nix`(**only values that differ from the built-ins**, ~30 leaves, incl. the two wallpaper-theming guards`appearance.wallpaperTheming.enableTerminal = false`/`enableAppsAndShell = true`that used to be dedicated options) are assigned to`settings`with`mkDefault`per leaf, so a profile's`settings`override them key by key. Everything else is internal: the package, the systemd unit (always on), and`liveKeys`(runtime state:`background.wallpaperPath`/`thumbnailPath`, `appearance.palette.accentColor`, `profile.avatarPath`/`avatarPicture`, `_presetMeta`— excluded from builtin-defaults.json, so they have no option). The non-null leaves are applied on each activation as`$live * $pinned`(Nix wins; keys Nix doesn't set are never touched, so they keep the built-in default or the menu value across restarts, reboots and switches). There is no editable-defaults tier: the old 860-line full-config`defaults.nix`is gone (it copied ~450 built-in values, which would all have been locked) and the former`~/.local/state/end4-pc/applied-defaults.json` is deleted on activation. Desktop widgets (`background.widgets.*`: enable flags, positions, visualizer/clock/world-clock options) are deliberately **not** set in Nix — they are configured from the menu and persist — and neither is `wallpaperSelector.sortMode`. Every pinned leaf is published to `~/.config/nixbook-shell/nix-managed.json`(red lock + disabled control via the vendored`NixManaged`singleton /`NixManagedBadge`; the `Config*.qml`controls take`configKey`) and its value to `nix-pinned-values.json`. The lock list is generated from the Nix attrsets at build time — nothing is hardcoded in QML — so deleting a key in Nix unlocks it: the activation runs after `linkGeneration`and calls`nixbook-shell ipc call nixManaged reload`(a file watch does not survive Home Manager swapping the symlink — verified), which re-reads the manifest, the pinned values and`config.json`in the running shell. The lock is enforced in the control itself: each`Config*.qml`carries a`Binding on enabled { when: root.nixManaged; value: false }`, so a page binding `enabled:`to something else can't re-enable a pinned control;`NixManaged.enforce()`runs 30 ms after every`Config`load and adapter write and restores any pinned leaf that drifted (custom controls, IPC, preset import, a slider writing its initial value), logging`[NixManaged] <path> is set in Nix; restoring it`. ## CI/CD Pipeline

**GitHub Actions Workflows (2 files):**

- `build.yaml` - Two jobs on the self-hosted runners (which share one Nix store). `build` builds all 5 profiles (totoro, anya, nishinoya, tanjiro, hanamichi) via matrix on push/PR to main; its `build (<profile>)` checks are the merge gate (steps run with `pipefail`, so a failing `colmena build` fails the check). `push-cache` runs on main/dispatch only, after all builds succeed, one profile at a time (`max-parallel: 1`): it re-resolves the system via `colmena build --keep-result` (a no-op evaluation on the shared store) and `nix copy`s it to the S3 cache, signing on upload (`secret-key=`) and retrying up to 5 times (each retry resumes, as already-uploaded paths are skipped). Concurrency: a new PR push cancels the old run and closing a PR cancels its pending run; main runs are never cancelled mid-flight. 120min timeout per job.
- `npins-update.yaml` - Automated dependency updates every 6 hours or manual dispatch. Updates each pin independently (max 10 parallel), syncs devenv.yaml nixpkgs revision, creates PRs with auto-merge.

## For AI Agents

### Important: Git Commit Policy

**AI agents MUST NEVER commit anything to this repository unless explicitly requested by the user.** This includes:

- Never creating commits automatically
- Never amending commits
- Never pushing to remote branches
- Never making any git commit operations without explicit user instruction

If you make changes, always present them for user review before committing.

### Important: Git Workflow

All git operations must follow this workflow. **Always ask the user for validation before performing any git action** (creating a branch, committing, pushing, rebasing, creating a PR, merging, deleting a branch) — never do it on your own initiative.

1. **Branch** - Never commit on `main`. Always create a dedicated feature branch first (`git checkout -b <branch-name>` from `main`), with a descriptive branch name.
2. **Commit** - Commit the changes on that branch (only after the user validated the changes).
3. **PR** - Push the branch and open a Pull Request against `main` (`git push -u origin <branch-name>` then `gh pr create`).
4. **Rebase** - Before updating the PR, rebase it on top of `main` and force-push (`git fetch origin && git rebase origin/main`, then `git push --force-with-lease`).
5. **Merge (deploy)** - The PR is merged into `main` only when the user wants to deploy the change. Merging is the deployment trigger: it requires explicit user validation, and the PR must have been rebased on `main` first. **Always use a rebase merge** (`gh pr merge <pr> --rebase`); if the base branch policy blocks it, add `--admin` (admin privileges are expected for this repo).
6. **Cleanup** - After the merge, delete the feature branch both remotely and locally (`git push origin --delete <branch-name>` if not auto-deleted, then `git branch -d <branch-name>`) and switch back to `main` (`git checkout main && git pull --ff-only`).

### When working with this project

1. **Configuration Files** - Always start with `base.nix`, `hive.nix`, and relevant profile
2. **Module System** - Use `nixosModules/` for system features, `homeManagerModules/` for user configs
3. **Per-Machine Customization** - Override in `profiles/{hostname}/` or user subdirectories

7. **Testing** - Use `default.nix` to build and test ISO

9. **Git Hooks** - Configured in `devenv.nix`, run automatically on commit
10. **Documentation** - Keep `README.md` and `AGENTS.md` updated; run `generate-docs` to update `docs/MODULES.md`
11. **AGENTS.md Updates** - Always update `AGENTS.md` after making changes to project structure, adding/removing machines, modules, packages, or features. This ensures the documentation stays accurate for future AI agents.
12. **Keybindings (`KEYBINDS.md`)** - Always check `KEYBINDS.md` when working with keybinds, and keep it up to date. Whenever you add, remove, or change a keyboard shortcut anywhere (compositor binds in `homeManagerModules/{niri,sway,hyprland}/`, terminal binds in `homeManagerModules/kittyConfig.nix`, Neovim mappings in `homeManagerModules/nixvim/`, or per-profile overrides in `profiles/*/*/`), update the matching table in `KEYBINDS.md` in the same change. Before assuming a key is free, grep these sources for the existing binding.
